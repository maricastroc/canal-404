# 0003: Competition backend with Prisma, Postgres and anonymous players

## Context

Stage 2 adds global boards, daily challenges and shared achievements. Until now everything lived in `localStorage`, and the portal had no server code besides pages. The portal is a hobby project for all ages, deployed on Vercel, so the backend has to be cheap, keep personal data to the minimum, and never be required to play.

## Decision

- **Where it runs.** Route Handlers in the same Next.js app (`src/app/api/*`). No separate service. Server-only code lives in `src/server`; rules shared with the browser live in `src/lib/competition`.
- **Database.** PostgreSQL through Prisma 7 with the `prisma-client` generator and the `@prisma/adapter-pg` driver adapter. Production uses Neon (pooled URL at runtime, direct URL for migrations); development and CI use a Postgres 17 container. The `pg` pool is registered with `attachDatabasePool` so Vercel closes idle connections before a function is suspended.
- **Schema.** `players`, `runs`, `personal_bests`, `daily_challenges`, `player_achievements` and `rate_limits`, with versioned migrations in `prisma/migrations`. Invariants Prisma cannot express (star range, non-negative scores, nickname length, the tag format, the challenge date format) are `CHECK` constraints in their own migration.
- **Identity.** A player is a nickname plus a random 256-bit key created by the server. The key is stored only as an `httpOnly`, `SameSite=Lax` cookie scoped to `/api`; the database keeps its SHA-256 hash. There is no email, password, real name or device fingerprint. Nicknames are not unique; a four-digit tag tells equal nicknames apart.
- **Nicknames.** 3 to 16 characters from Latin letters, digits, space, hyphen and underscore, at least one letter, no runs of six or more digits (phone or document numbers). A word filter blocks offensive words, including leetspeak and stretched letters, and reserves staff names. The same check runs in the browser for instant feedback and on the server as the authority. A `hidden` status removes a player from public boards without telling them; `banned` refuses their requests.
- **Run tickets.** Every match asks for a ticket when it starts. A ticket is signed with HMAC-SHA256 (`COMPETITION_SECRET`), carries the game, the level, a server seed, the issue time and the player when known, and is valid for 12 hours. A ticket can be used once: `runs.ticket_id` is unique, so a retried submission returns the stored result instead of a duplicate. Tickets issued before the player chose a nickname can still be redeemed right after joining.
- **Submissions.** The server validates the payload with zod, recomputes the score, stars and ranking keys from the submitted stats (see [0004](0004-result-validation.md)), checks the time since the ticket, and writes the run and the personal best in one transaction. The personal best row is locked with `SELECT … FOR UPDATE` and replaced with `INSERT … ON CONFLICT DO UPDATE … WHERE (new) > (old)`, so concurrent submissions keep the best one and equal results keep the earliest.
- **Boards.** One row per player and board in `personal_bests`. A board is ordered by three integer keys (higher is better; "lower is better" metrics are stored negated), then by `achieved_at`, then by run id, with a matching index. A player's position is one plus the number of visible rows ahead of them.
- **Abuse limits.** Fixed-window counters in `rate_limits`, keyed by player id or by an HMAC of the address (the raw address is never stored). Per-address limits are generous because schools and families share one address; per-player limits are tighter. Eight rejected results in an hour pause that player's submissions for the hour. Requests from other sites are refused (`Origin` / `Sec-Fetch-Site`), bodies must be JSON and have size limits.
- **Outages.** Without `DATABASE_URL` or a 32-character `COMPETITION_SECRET`, `/api/status` answers `unconfigured` and every other route answers 503 `unconfigured`. When the database is unreachable, `/api/status` answers `offline` and routes answer 503 `unavailable` without details. The browser checks the status once a minute, never blocks a game on the network (six-second timeouts), and keeps results that failed to send in a versioned outbox (`canal404:outbox:v1`, at most ten, while their tickets are valid).
- **Retention.** A daily Vercel Cron (`/api/cron/cleanup`, protected by `CRON_SECRET`) deletes rate-limit windows after 2 days, rejected runs after 30 days, runs that are no longer a personal best after 90 days, and players not seen for two years. "Sair do placar" deletes the player and, by cascade, all their runs, records and achievements immediately.

## Consequences

- The game code never touches the network; the shell (`GameShell.tsx`) owns tickets and submissions, just as it owns telemetry.
- Losing the cookie (clearing site data, another browser) means a new identity. There is no recovery yet; a recovery code can be added later without changing the schema.
- Changing a ranking rule means bumping the rule version, which starts a new board id (`<game>/<level>/v<n>`) instead of mixing old and new results.
- Running the database tests needs Postgres (`npm run db:up`, then `npm run test:db`). Without `TEST_DATABASE_URL` they are skipped locally; CI sets `REQUIRE_DB_TESTS` so they can't be skipped there.
